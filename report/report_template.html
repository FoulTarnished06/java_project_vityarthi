Chapter 1: Introduction & Problem Statement

1.1 Background

In the digital economy, modern banking infrastructures rely upon mission-critical software systems designed for stringent transactional integrity, high availability, and deterministic data preservation. At their core, financial institutions demand strict adherence to ACID principles (Atomicity, Consistency, Isolation, and Durability) to ensure that customer funds are never lost, duplicated, or misallocated.

1.2 Problem Statement

Academic software projects frequently simplify banking applications into rudimentary procedural scripts that store balances in primitive variables without state persistence, fail to enforce type-specific financial rules (such as minimum balances or overdraft facilities), and ignore transaction atomicity during inter-account transfers. A single failed step during a transfer can result in funds vanishing or being credited twice.

1.3 Project Objectives

The primary objectives of the Banking & Transaction Simulation System are:

  • Model Real-World Banking Products: Establish distinct account tiers (Savings Accounts with interest accrual and minimum balances vs. Checking Accounts with overdraft facilities and maintenance fees).
  • Ensure Transactional Atomicity: Guarantee that two-party fund transfers either succeed fully or undergo an immediate rollback if any validation or target constraint fails.
  • Cryptographic Security: Implement SHA-256 salted hashing for user authentication PINs, preventing plaintext password vulnerabilities.
  • Zero-Dependency Durability: Store all customer accounts and transaction ledgers on disk via structured CSV repositories, eliminating runtime setup bottlenecks.
  • Interactive Dual-Portal Experience: Provide customer operations (deposits, withdrawals, transfers, account statements) and manager administration (total bank liquidity, interest accrual, account freezing).

Chapter 3: System Architecture & OOP Design

3.1 Architectural Overview

The system follows a clean, decoupled 4-tier architectural pattern:

+-----------------------------------------------------------------------+ | PRESENTATION LAYER (CLI) | | com.bank.Main -> Input validation, ANSI menus, interactive workflows| +-----------------------------------+-----------------------------------+ | v +-----------------------------------------------------------------------+ | SERVICE / BUSINESS LAYER | | com.bank.service.BankService -> Atomic transfers, interest logic | | com.bank.service.SecurityUtil -> SHA-256 salted PIN hashing | +-----------------------------------+-----------------------------------+ | v +-----------------------------------------------------------------------+ | DATA ACCESS LAYER | | com.bank.repository.AccountRepository (Interface) | | com.bank.repository.FileAccountRepository (CSV Data Persistence) | +-----------------------------------+-----------------------------------+ | v +-----------------------------------------------------------------------+ | DOMAIN MODEL LAYER | | Account (Abstract Base Class) | | ├── SavingsAccount (Min balance, 4.5% interest accrual) | | └── CheckingAccount (Overdraft limit $500, overdraft fee $15) | | Customer, Transaction, TransactionType | +-----------------------------------------------------------------------+

3.2 Application of OOP Principles

  • Abstraction: The Account class defines the abstract contract withdraw() and getAccountType(), hiding specific overdraft calculations or minimum balance constraints from callers.
  • Encapsulation: Sensitive state variables such as balance and pinHash are marked protected/private and manipulated only via synchronized mutator methods with validation guards.
  • Inheritance: SavingsAccount and CheckingAccount inherit common attributes (account number, holder customer, balance, transaction history) while customizing financial behavior.
  • Polymorphism: The BankService manages polymorphic Account collections seamlessly without needing to know concrete subclass types during deposits, transfers, or balance queries.

Chapter 4: Implementation Details & Core Algorithms

4.1 Atomic Inter-Account Transfer Algorithm

To prevent race conditions and partial failures, inter-account transfers are implemented with strict rollback capability: 

public synchronized void transfer(String fromAccNum, String pin, String toAccNum,
                                 double amount, String notes) throws BankingException {
    // 1. Validation guards
    if (fromAccNum.equalsIgnoreCase(toAccNum))
        throw new BankingException("Cannot transfer to the same account.");

    Account sender = authenticate(fromAccNum, pin);
    Account recipient = getAccount(toAccNum);

    if (!recipient.isActive())
        throw new BankingException("Recipient account is frozen.");

    double senderSnapshot = sender.getBalance();

    // 2. Atomic Transaction Execution
    try {
        sender.withdraw(amount, "Transfer to " + recipient.getAccountNumber());
        recipient.deposit(amount, "Transfer from " + sender.getAccountNumber());

        repository.save(sender);
        repository.save(recipient);
    } catch (Exception e) {
        // 3. Rollback mechanics
        sender.restoreBalance(senderSnapshot);
        throw new BankingException("Transfer failed and was rolled back: " + e.getMessage(), e);
    }
}

4.3 Overdraft & Minimum Balance Enforcement

  • Savings Account: Requires balance - amount >= minimumBalance ($100.00). If violated, an InsufficientFundsException is thrown.
  • Checking Account: Permits balance - amount >= -overdraftLimit ($500.00). When crossing into negative balance, an automated $15 overdraft protection fee is assessed.

Chapter 7: Conclusion & Future Enhancements

7.1 Project Conclusion

The Banking & Transaction Simulation System successfully achieves all of its initial design goals. By modeling real-world banking products through Object-Oriented principles, the software demonstrates clear architectural separation between domain entities, business logic, persistence services, and user interfaces.

Key achievements include:

  • Implementation of polymorphic account types (Savings and Checking) with distinct financial rules.
  • Fail-safe, atomic inter-account transfer execution with automatic rollback upon error.
  • Zero external dependencies, ensuring compatibility with standard Java environments.
  • Complete audit trails with persistent CSV storage.
  • 100% automated test coverage across all critical edge cases and financial boundary conditions.

7.2 Future Scope & Enhancements

While the current simulation meets all academic requirements, several viable avenues for future expansion include:

  1. Graphical User Interface (GUI): Developing a JavaFX or Swing desktop client featuring dynamic charts for expense and savings growth.
  2. Relational Database Integration: Transitioning the persistence layer from CSV files to a JDBC-backed SQLite or PostgreSQL database with schema migrations.
  3. RESTful API Architecture: Refactoring the service layer into a Spring Boot microservice to expose JSON endpoints for mobile and web clients.
  4. Multi-Factor Authentication (MFA): Incorporating time-based one-time password (TOTP) generators for high-value transactions.
